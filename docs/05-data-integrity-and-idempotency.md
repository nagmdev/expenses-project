# 05 - سلامة البيانات ومنع التكرار (Data Integrity & Idempotency)

> هذا المستند يصف المعمارية الحالية بعد إصلاح مشاكل التكرار (Duplicates) وحالات السباق (Race Conditions).
> يحلّ محل ما ورد في المستندات السابقة عن استخدام `localStorage` كمخزن للبيانات.

---

## 1. مصدر واحد للحقيقة (Single Source of Truth)

```
Frontend (React)
   │  mutation (مع Idempotency Key)
   ▼
Domain layer  (src/domain/*)  ── عملية ذرية واحدة (Firestore Transaction)
   │                               ├─ السجل التجاري (طلب / حساب / عهدة …)
   │                               ├─ حركة دفتر الأستاذ + تحديث الرصيد
   │                               ├─ مفتاح التفرد (uniqueKeys)
   │                               ├─ سجل التدقيق (auditLogs)
   │                               └─ حدث الإشعار (outbox)
   ▼
Cloud Firestore  ──► onSnapshot (مستمع واحد لكل مجموعة) ──► React state
```

- **Cloud Firestore هو المصدر الوحيد لبيانات الأعمال.** لا توجد كتابة مزدوجة إلى Express/SQLite.
- **`localStorage` لم يعد قاعدة بيانات**: يُستخدم فقط لتفضيلات العرض (الشركة/التبويب النشط). يتم حذف مفاتيح البيانات القديمة تلقائياً عند التحميل.
  كاش Firestore الرسمي (IndexedDB – آمن بين التبويبات) هو كاش التشغيل السريع ودون اتصال.
- **لا توجد كتابة إلى قاعدة البيانات من داخل `useEffect`** (أُزيلت تأثيرات "الإصلاح الذاتي" التي كانت تنشئ أعضاء وبطاقات خزينة، وتحذف قيوداً مالية ظنّتها مكررة، وقد تُصفّر أرصدة).
- الخادم `server/` (Express + SQLite) **لا يستخدمه التطبيق**؛ بقي كمرجع مستقل تم إصلاحه (انظر القسم 6).

## 2. منع التكرار (Idempotency)

| الطبقة | الآلية |
| :--- | :--- |
| الواجهة | `useSubmitGuard()` قفل متزامن (`useRef`) — النقر المزدوج / Enter + نقرة لا ينفّذان مرتين |
| الواجهة | مفتاح عملية (Idempotency Key) ثابت لكل "نية" مستخدم؛ يُعاد استخدامه عند إعادة المحاولة ويتغيّر فقط بعد النجاح |
| السياق | `singleFlight` يدمج الاستدعاءات المتزامنة المتطابقة في استدعاء واحد |
| قاعدة البيانات | معرّف السجل مشتق من المفتاح (`req-<key>`, `vault-<key>` …) + قراءة داخل Transaction: إن وُجد السجل يُعاد كما هو دون أي أثر جانبي |

النتيجة: نقرة، نقرتان، 10 نقرات، Enter + نقرة، انقطاع الشبكة ثم إعادة المحاولة، تبويبان — **سجل واحد فقط**.

## 3. الترقيم والتفرد

- أرقام الطلبات/العهد/التأشيرات تصدر من عدّاد ذري `counters/{name}` داخل نفس الـ Transaction
  (`REQ-2026-000001`, `CUS-2026-00001`, `VISA-2026-000001`). قواعد الأمان تسمح بزيادة العداد بمقدار 1 فقط.
- Firestore لا يدعم UNIQUE؛ البديل هو مستند مفتاح لكل قيمة فريدة في `uniqueKeys` يُقرأ ويُنشأ مع الكيان في نفس العملية:
  رقم الحساب/المحفظة داخل الشركة، كود بند الصرف، اسم المورد، اسم القسم، بريد الموظف داخل الشركة، كود الشركة.

## 4. الصحة المالية

- كل حركة رصيد تُحسب من الرصيد المقروء **داخل** الـ Transaction (لا فقدان تحديثات عند السحب المتزامن).
- إنشاء الحساب + قيد الرصيد الافتتاحي عملية واحدة؛ إنشاء الشركة + بطاقاتها الأربع الافتراضية عملية واحدة.
- الصرف: حالة الطلب + خصم الحساب (والحساب البنكي الأم لإنستاباي/المحفظة) + قيد الدفتر + ميزانية البند + إجمالي المورد + التدقيق + الإشعار — عملية واحدة.
  معرّف قيد الصرف حتمي (`tx-req-<requestId>`) والطلب المصروف لا يُصرف مرة أخرى أبداً (`already_disbursed`).
- آلة الحالات محمية: `pending → approved` مرة واحدة؛ تكرار الاعتماد لا يُنشئ حدثاً ثانياً ولا بريداً ثانياً؛ `disbursed` حالة نهائية.
- تعديل مبلغ طلب معتمد يعيده إلى `pending` لإعادة الاعتماد. حقول الرصيد لا تُعدَّل إلا عبر حركات الدفتر.
- دفعات التأشيرات تُسجَّل في دفتر الأستاذ الصحيح `accountTransactions` ولا يمكن أن تتجاوز التكلفة حتى مع الدفع المتزامن.

## 5. الإشعارات (Outbox)

```
Transaction ──► outbox/{eventId} (pending)
                    │  claim (Transaction + lease) — مُرسِل واحد فقط
                    ▼
             /api/send-email  (Idempotency-Key, مهلة 10–15 ثانية)
                    │
      sent │ failed (إعادة محاولة بتأخير أُسّي 30s→1h) │ dead (بعد 6 محاولات أو خطأ دائم)
```

- `eventId` حتمي (`new_request__<requestId>` …) — تكرار العملية لا يُنشئ بريداً ثانياً.
- يُسجَّل المستلمون الذين وصلهم البريد (`deliveredTo`) فلا يُعاد الإرسال لهم عند إعادة المحاولة.
- عامل إعادة المحاولة يعمل في جلسات المدراء كل دقيقة؛ فشل مزود البريد لا يُفشل العملية التجارية أبداً.
- الـ Webhook يستقبل `eventId` في الجسم وفي الترويسات `Idempotency-Key` / `X-Event-Id` — **على المستقبِل تجاهل eventId سبق معالجته.**
- سجل البريد في الإعدادات يُعرض من مستندات الـ outbox (مع السجل القديم `email_logs`).
- إعدادات البريد أصبحت مشتركة في `system_settings/email_notifications` (مفتاح الـ API لا يُخزَّن في قاعدة البيانات — يبقى في متغيرات Vercel).

## 6. خادم Express (مرجعي)

- معرّفات UUID ويُحترم معرّف العميل (إعادة POST بنفس المعرف لا تنشئ سجلاً ثانياً).
- ترويسة `Idempotency-Key`: تُخزَّن الاستجابة في نفس الـ Transaction وتُعاد عند التكرار (`Idempotent-Replayed: true`)، ونفس المفتاح مع محتوى مختلف → 422.
- تسلسل ذري لأرقام الطلبات + فهارس UNIQUE، وانتقالات حالة مشروطة (`WHERE status = ?`)، والصرف في Transaction واحدة.

## 7. خطوات النشر (مهم)

1. **انشر قواعد الأمان الجديدة `firestore.rules`** (من Firebase Console ← Firestore ← Rules، أو `firebase deploy --only firestore:rules`).
   بدونها سترفض قاعدة البيانات مسارات الإنشاء الجديدة (قراءة المستند غير الموجود داخل الـ Transaction، العدّادات، الـ outbox، التأشيرات، الإعدادات).
2. انشر الواجهة و`api/send-email.ts` على Vercel كالمعتاد.
3. بعد النشر: يجب على المشرف العام حفظ إعدادات البريد مرة واحدة من صفحة الإعدادات إن لم تُنقل تلقائياً.
4. **البيانات المكررة القديمة** الموجودة فعلاً في قاعدة البيانات لم تعد مخفية في الواجهة (الإخفاء كان يُخفي أيضاً سجلات حقيقية ويحذف قيوداً مالية). راجعها ونظّفها يدوياً مرة واحدة.

## 9. استرجاع البيانات المحفوظة محلياً (النسخة القديمة)

النسخة القديمة كانت تحفظ في `localStorage` أولاً وتتجاهل أخطاء Firestore، فبعض السجلات لم تصل لقاعدة البيانات أبداً (كل طلبات التأشيرات، وأقسام أنشأها مديرو الشركات). هذه المفاتيح **لا تُحذف تلقائياً أبداً** الآن.

- يظهر تنبيه أعلى الموقع عند وجود بيانات قديمة على المتصفح، ومن الإعدادات: «استرجاع بيانات محلية / نسخة احتياطية».
- **استرجاع فعلي** (إنشاء الناقص فقط، دون أي تعديل أو حذف): طلبات التأشيرات (محددة افتراضياً)، طلبات الصرف، الأقسام، البنود، الموردين.
- **نسخة احتياطية فقط** (لا تُكتب أبداً للقاعدة): الحسابات، الحركات المالية، العهد، التسويات، الموظفين، الشركات — لأن نسخة قديمة منها قد تُفسد الأرصدة أو تعيد صلاحيات أُلغيت.
- كل استرجاع يترك علامة دائمة `legacyRestores/{collection}__{id}` + سجل تدقيق باسم الشركة، فالسجل المسترجع ثم المحذوف عمداً لا يعود مرة أخرى.
- الطلبات/التأشيرات بحالة غير «قيد المراجعة» يسترجعها المشرف العام فقط (قواعد الأمان تسمح له وحده بإنشائها بأي حالة).
- يمكن تنزيل نسخة احتياطية JSON من أي متصفح واستيرادها من متصفح المشرف العام.
